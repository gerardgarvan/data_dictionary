## Decisions

### D-23 — Per-file encoding for Windows-1252 sources (LOCKED 2026-10-25, Gerard)

7 source files contain Windows-1252 byte 0xDF (ß, decimal 223) in the
`Base_Procedure_1` column.  SAS reads these as `encoding='wlatin1'` and
transcodes to UTF-8 internally.  ASCII bytes (0x00–0x7F) are identical in
both encodings, so no other values are affected.

**Files with encoding='wlatin1':**
- s03: 2018_2019_CPT_ROLLUP_X_MASTER_DATASET_20200801.csv
- s07: 2018_2019_X_MASTER_DATASET_20200801.csv
- s09: 2018_2022_X_MASTER_DATASET_20240402.csv  (spine)
- s10: 2020_CPT_ROLLUP_X_MASTER_DATASET_20210609.csv
- s12: 2020_X_MASTER_DATASET_20210519.csv
- s15: 2021_X_MASTER_DATASET_20230512.csv
- s17: 2022_MASTER_DATASET_20231024.csv

All other files (including all XLSX) stay `encoding='utf-8'`.

**Implementation:**
- `work.file_list` in `03a_build_spec.sas` gains a `src_encoding` column
  (`wlatin1` for the 7 above; `utf-8` for all others).
- `pdd.import_spec` and `docs/import_spec_generated.csv` gain a
  `src_encoding` column (11th field in CSV).
- `03_import.sas` reads `src_encoding` from the spec CSV and writes
  `encoding='<src_encoding>'` into each generated INFILE statement instead
  of the former hardcoded `encoding='utf-8'`.
- Override CSVs (`import_spec_overrides.csv`) also read the `src_encoding`
  column for consistency; default is `utf-8` if the field is blank (backward
  compatibility).

**Post-import assertion — `%p3_assert_encoding`:**
Defined at the bottom of `03a_build_spec.sas` and available for call at
the end of `03_import.sas` (or after the full import block).

- Loops over `pdd.src_s01..pdd.src_s20` (skips XLSX: s06/s08/s11/s19).
- For each dataset, queries `dictionary.columns` for character columns.
- Checks every character value with `verify(val, collate(0,127)) > 0`.
  This detects any byte > 127 (includes 0xDF = 223).  Available in
  Base SAS without options; no `kvalidate` needed.
- On violation: writes `ERROR:` to the log with s_code, column name, row
  count.  No values are printed.
- After applying `wlatin1` encoding on the 7 affected files, this guard
  should produce 0 violations.

**Diagnostic tool:**
`tools/scan_source_encoding.py` — read-only scan of source CSV files.
Reports file, line number, byte offset, and hex for any non-UTF-8 sequence.
Exit 0 if clean, exit 1 if issues found.  `--check SPEC_CSV` mode verifies
the spec has the correct encoding for each file.

## Implementation notes

- The pre-pass INFILE in `03a_build_spec.sas` (Section 4) still uses
  `encoding='utf-8'` for the raw char-length scan.  This is intentional:
  the pre-pass reads each column as `$32767` to measure max lengths, not to
  parse values.  SAS will silently replace invalid UTF-8 bytes with a
  substitution character in this context; the measured length is not
  affected.  The correct encoding is applied only in the import DATA step
  (generated by `03_import.sas`).
- `pdd.import_spec` Assert 3 (C row informat length = spec length) is
  unchanged; `src_encoding` does not affect length derivation.
- Assert 4 (XLSX C lengths >= measured xlsx_max_len) is unchanged.
- `_assert_spec_complete` checks 20 distinct file_codes; unchanged.
